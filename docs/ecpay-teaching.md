# 綠界 ECPay 金流串接：逐步教學

這份文件用你這個「抖內／請我喝咖啡」的實作，帶你把金流串接的每個環節搞懂。
讀完你會知道：一筆線上刷卡從按下按鈕到入帳，中間到底發生了什麼事。

> 這是你第一次串金流，所以我把「為什麼」寫得比「怎麼做」還多。
> 程式碼都已經寫好在專案裡，這裡是對照著讀的地圖。

---

## 0. 先建立正確的心智模型

線上金流最重要的一個觀念：**你的網站不會經手信用卡號**。

流程其實是這樣的（先看懂這張圖，後面就簡單了）：

```
使用者          你的網站(Next.js)         綠界 ECPay          發卡銀行
  │                   │                       │                  │
  │ 1.輸入金額按贊助   │                       │                  │
  │ ────────────────► │                       │                  │
  │                   │ 2.建立訂單+算簽章       │                  │
  │                   │ ────────────────────► │                  │
  │ 3.被自動導到綠界付款頁                      │                  │
  │ ◄─────────────────────────────────────── │                  │
  │ 4.在「綠界」頁面輸入卡號                     │                  │
  │ ──────────────────────────────────────► │ 5.向銀行請款 ────► │
  │                   │                       │ ◄─────────────── │
  │                   │ 6a.伺服器通知(ReturnURL)│                  │
  │                   │ ◄──────────────────── │                  │
  │ 6b.瀏覽器導回(OrderResultURL)              │                  │
  │ ◄─────────────────────────────────────── │                  │
```

重點：
- **卡號只在綠界的頁面上輸入**，永遠不會經過你的伺服器 → 你不用處理 PCI 合規那些惡夢。
- 你的責任只有兩件事：**正確地把訂單送出去**、**正確地驗證回來的結果**。

## 1. 三組金鑰是什麼？

打開 `.env.local.example`，金流有三個值：

```env
ECPAY_MERCHANT_ID=2000132          # 商店代號：你是誰
ECPAY_HASH_KEY=5294y06JbISpM5x9    # 加簽金鑰
ECPAY_HASH_IV=v77hoKGq4kWxNNIS     # 加簽向量
```

- `MerchantID`：綠界給你的商店編號。上面這組 `2000132` 是綠界**公開的測試商店**，
  大家都能用來測試，刷了也不會真的扣錢。
- `HashKey` / `HashIV`：拿來產生「簽章」（CheckMacValue）的鑰匙。
  **絕對不能外洩**，也絕對不能寫進前端。所以我們放在 `.env.local`（不進 git）。

> 上線時：到綠界正式後台申請自己的商店，拿到你自己的這三個值換上去，
> 再把 `ECPAY_ENV` 改成 `production`。

## 2. CheckMacValue：整個金流的靈魂

這是最容易卡關、也最重要的部分。程式在 [`src/lib/ecpay.ts`](../src/lib/ecpay.ts)。

**它要解決的問題**：綠界怎麼知道「這筆 120 元的訂單真的是你送的，而不是有人在
中途把金額改成 1 元」？答案是**簽章**——用只有你和綠界知道的 HashKey/HashIV，
對所有參數算出一個指紋。任何一個參數被改，指紋就對不上。

產生步驟（`genCheckMacValue()`）：

1. **把參數依名稱 A→Z 排序**
2. **前後夾上金鑰**，組成：`HashKey=xxx&參數1=值1&參數2=值2&...&HashIV=xxx`
3. **整串做 URL encode，再轉小寫**（要模仿 .NET 的編碼方式，這是最多人踩雷的地方，
   見 `dotNetUrlEncode()`——`+`、`!`、`(`、`)`、`*`、`-`、`.`、`_` 這些字元的處理要跟綠界一致）
4. **SHA256 雜湊，最後轉大寫**

綠界收到後會用**一模一樣**的步驟自己算一次，兩邊一致才放行。
所以你的算法只要有一個字元不同，就會一直收到「CheckMacValue Error」。

> 💡 除錯技巧：如果一直簽章錯誤，把你組出來的那串「排序後字串」印出來，
> 跟綠界文件的範例逐字比對，通常是某個參數多了/少了、或編碼差一個字元。

## 3. 送出訂單（Step 1~3）

### 前端：[`src/components/tip-jar.tsx`](../src/components/tip-jar.tsx)
使用者選金額、填暱稱留言，按下贊助 → `POST /api/tip/create`。
拿到回應後，前端**動態組一個隱藏 form，auto-submit** 到綠界結帳頁：

```js
const form = document.createElement("form");
form.method = "POST";
form.action = data.action;              // 綠界結帳網址
Object.entries(data.params).forEach(([k, v]) => { /* 每個參數塞成 hidden input */ });
document.body.appendChild(form);
form.submit();                          // 這一步把使用者帶去綠界
```

為什麼用 form submit 而不是 fetch？因為我們需要**讓瀏覽器整頁跳轉**到綠界的網域，
fetch 只能拿資料回來、不會帶使用者過去。

### 後端：[`src/app/api/tip/create/route.ts`](../src/app/api/tip/create/route.ts)
1. 驗證金額（1 ~ 100,000）。
2. 產生一個 ≤20 碼的訂單編號 `MerchantTradeNo`（綠界規定英數、且**每筆都要唯一**）。
3. 若已設定 Firebase，在 `donations` 集合建一筆 `pending`（之後付款成功再更新）。
4. 用 `buildCheckoutParams()` 組出全部參數 + `CheckMacValue`，回傳給前端。

關鍵參數說明：

| 參數 | 意義 |
|---|---|
| `MerchantTradeNo` | 你的訂單編號，唯一 |
| `TotalAmount` | 金額（整數） |
| `ItemName` | 商品名稱（會顯示在綠界頁面）|
| `ReturnURL` | **伺服器**通知網址（最重要，見下一節）|
| `OrderResultURL` | 付款後**使用者瀏覽器**導回的網址 |
| `ChoosePayment` | `ALL` = 讓使用者自己選信用卡／ATM／超商 |
| `CheckMacValue` | 上面算出的簽章，一定要最後放 |

## 4. 收到結果：兩條回來的路（Step 6）

付款完成後，綠界會用**兩條不同的路**通知你，這是新手最容易搞混的地方：

### 路 A：ReturnURL —— 伺服器對伺服器（可信）
[`src/app/api/tip/callback/route.ts`](../src/app/api/tip/callback/route.ts)

綠界的**伺服器**直接 POST 到你的伺服器。這條路**最可信**，因為它不經過使用者的瀏覽器，
不會被竄改、也不會因為使用者關掉頁面就漏掉。**真正該用來更新「付款成功」的，是這條。**

它做三件事：
1. `verifyCallback()` 驗證 CheckMacValue（確認不是偽造的通知）。
2. `RtnCode === "1"` → 付款成功 → 把 `donations` 那筆更新成 `paid`。
3. **回傳純文字 `1|OK`**。這一步不能忘——綠界沒收到 `1|OK` 會以為你沒收到，
   然後每隔一段時間**重送**通知，直到你回 `1|OK` 為止。

### 路 B：OrderResultURL —— 瀏覽器導回（只負責畫面）
[`src/app/api/tip/return/route.ts`](../src/app/api/tip/return/route.ts) → 轉址到
[`src/app/tip/thanks/page.tsx`](../src/app/tip/thanks/page.tsx)

綠界用**使用者的瀏覽器**POST 一份結果回來（所以這裡是 POST handler，不是一般的 page）。
我們驗證後用 303 轉去一個純顯示的「謝謝你的咖啡 ☕」感謝頁。

> ⚠️ 為什麼不直接相信路 B 就好？因為使用者可能付完款、在導回前就把分頁關掉，
> 那你的畫面雖然沒更新，但錢其實已經收到了。所以**帳務以路 A 為準，路 B 只給使用者看**。

## 5. 本機怎麼測試

```bash
npm run dev
```

到首頁「請我喝咖啡」→ 輸入金額 → 送出。你會被導到綠界**測試付款頁**。

**測試信用卡號**（綠界公開測試卡，不會真的扣款）：
- 卡號：`4311-9522-2222-2222`
- 有效月年：任何未過期的日期（例如 `12/26`）
- 安全碼：任意三碼（例如 `222`）

付款完成後會導回你的感謝頁。

### ⚠️ 本機的限制：ReturnURL 收不到
路 A（伺服器通知）需要一個**外部網際網路連得到的網址**，而 `localhost` 只有你自己連得到，
綠界的伺服器打不到。所以本機測試時：
- 路 B（畫面導回感謝頁）✅ 會正常運作。
- 路 A（自動把訂單更新成 `paid`）❌ 不會觸發，後台的抖內紀錄會停在 `pending`。

**兩個解法**：
1. **用 ngrok 把 localhost 暴露出去**（推薦練習用）：
   ```bash
   npx ngrok http 3000
   ```
   把它給你的 `https://xxxx.ngrok-free.app` 填進 `.env.local` 的 `NEXT_PUBLIC_SITE_URL`，
   重啟 dev，這樣綠界就打得到你的 callback 了。
2. **直接部署到線上**（Vercel），用正式網址測，callback 自然就通了。

## 7. 延伸：這套流程還能拿來做什麼？

你現在會的這套「建單 → 簽章 → 導轉 → 驗簽回寫」流程，其實就是**所有電商金流的骨架**。
把「抖內」換成「商品訂單」，加上購物車與出貨狀態，就是一個完整的電商後台。
綠界同一組 API 也支援 ATM、超商代碼、定期定額，參數改一改就能擴充。
